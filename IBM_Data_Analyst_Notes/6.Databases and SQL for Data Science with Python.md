# Why Databases Beat Spreadsheets

*(Distilled from the course dialogue — my own comparison, worth keeping for interviews.)*

**1. Concurrent access (multi-user control).** Spreadsheets hit version conflicts, locked files, and overwrites when several people edit at once. Databases use **concurrency control**: row-level locking lets thousands of users read/write different rows simultaneously, and **ACID transactions** guarantee that, e.g., two people booking the last airline seat can't both succeed.

**2. Data quality & integrity.** Spreadsheets accept "one hundred" in a numeric column or a blank Customer ID. Databases enforce:
- **Schema enforcement** — wrong data type is rejected outright
- **Constraints** — `NOT NULL`, `UNIQUE`, `CHECK`
- **Referential integrity (foreign keys)** — can't delete a customer who still has orders; no orphaned rows

**3. Organization & reduced redundancy.** Spreadsheets repeat data (customer address written on all 5 of their orders). **Normalization** splits data into related tables (Customers, Orders, Products) linked by primary/foreign keys — update the address once, it's correct everywhere.

**4. Performance & scale.** Spreadsheets lag past ~100K rows. Databases handle millions/billions of rows using **indexes** (like a textbook index — find data in milliseconds without a full scan) and answer complex multi-table questions with a single SQL query.

| Feature | Spreadsheet | Relational DB |
|---|---|---|
| Data size | Small–medium (~1M row hard cap, slows far earlier) | Virtually unlimited (terabytes) |
| Data entry | Flexible, error-prone | Strict types & rules |
| Redundancy | High (repeated data) | Low (normalized, related tables) |
| Multi-user | Locking/overwrite issues | Thousands of concurrent users |
| Speed/search | Degrades on large sheets | Optimized via indexes & queries |

**Everyday database examples:** phone apps (SQLite), streaming services (playlists, playback position), e-commerce (inventory, transactions, tracking), ride-sharing (spatial DBs matching live GPS data), online banking (secure, consistent transactions).

**SQL = Structured Query Language.** Core verbs: `SELECT` (query), `INSERT`/`UPDATE`/`DELETE` (manipulate), `CREATE`/`ALTER`/`DROP` (define structure), `COMMIT`/`ROLLBACK`/`SAVEPOINT` (transaction control). It's the gateway skill for analysts, scientists, and engineers — without it you can't reach the raw data that powers every analysis.

# Module 1 — Basic SQL

## SELECT

`SELECT` is a **Database Query (DQL)** command that retrieves data from a table.

```sql
SELECT column1, column2 FROM table_1;      -- named columns
SELECT * FROM table_1;                     -- all columns
SELECT * FROM table_1 WHERE <predicate>;   -- filtered rows
```

Worked examples on a `COUNTRY(ID, Name, CCode)` table:

```sql
SELECT * FROM COUNTRY;                    -- entire table
SELECT ID, Name FROM COUNTRY;             -- two columns only
SELECT * FROM COUNTRY WHERE ID <= 5;      -- rows 1–5
SELECT * FROM COUNTRY WHERE CCode = 'CA'; -- only Canada's row
```

## Cheat sheet: SELECT, WHERE, COUNT, DISTINCT, LIMIT, INSERT, UPDATE, DELETE

| Command | Purpose | Syntax | Example |
|---|---|---|---|
| SELECT | Fetch data | `SELECT col1, col2 FROM table;` | `SELECT city FROM placeofinterest;` |
| WHERE | Filter rows by condition | `SELECT ... FROM table WHERE condition;` | `SELECT * FROM placeofinterest WHERE city = 'Rome';` |
| COUNT | Count non-NULL rows in a column | `SELECT COUNT(col) FROM table;` | `SELECT COUNT(country) FROM placeofinterest WHERE country = 'Canada';` |
| DISTINCT | Unique values only | `SELECT DISTINCT col FROM table;` | `SELECT DISTINCT country FROM placeofinterest WHERE type = 'historical';` |
| LIMIT | Cap number of rows returned | `SELECT * FROM table LIMIT n;` | `SELECT * FROM placeofinterest WHERE airport = 'pearson' LIMIT 5;` |
| INSERT | Add new rows | `INSERT INTO table (c1, c2) VALUES (v1, v2);` | `INSERT INTO placeofinterest (name, type, city, country, airport) VALUES ('Niagara Falls', 'Nature', 'Toronto', 'Canada', 'Pearson');` |
| UPDATE | Modify existing rows | `UPDATE table SET c1 = v1 WHERE condition;` | `UPDATE placeofinterest SET name = 'Niagara Falls' WHERE name = 'Niagara Waterfalls';` |
| DELETE | Remove rows | `DELETE FROM table WHERE condition;` | `DELETE FROM placeofinterest WHERE city IN ('Rome', 'Vienna');` |

> [!warning] Omitting WHERE
> `UPDATE` or `DELETE` **without WHERE** hits **every row** in the table. `DELETE FROM t;` empties the table (the table itself remains).

## Module 1 summary

- **DML** statements (SELECT, INSERT, UPDATE, DELETE) read and modify data.
- The `WHERE` clause uses a **predicate** to refine results.
- `COUNT`, `DISTINCT`, `LIMIT` are expressions used with SELECT.

## Quiz takeaways (Basic SQL)

- Databases are data repositories; multiple types exist (relational, hierarchical, NoSQL); they store data **and** allow queries. Not all databases use fixed rows/columns.
- Retrieve data → `SELECT`. Add rows → `INSERT INTO ... VALUES (...)`.
- Query returning all rows instead of a filtered set → missing `WHERE` clause (e.g., `WHERE ReleaseYear = 2019`).
- `SELECT DISTINCT FIRSTNAME` → unique first names only.
- `SELECT COUNT(DISTINCT FIRSTNAME)` → the **number** of unique first names.
- `UPDATE INSTRUCTOR SET LASTNAME = 'Brewster' WHERE LASTNAME = 'Smith'` → changes **all** Smiths to Brewster.
- `WHERE LASTNAME = 'Smith' LIMIT 5` → the **first 5 matching** rows, filter applies before limit.

# Module 2 — Relational Databases and Tables (DDL)

## DDL vs DML

| Category | Statements | Acts on |
|---|---|---|
| **DDL** (Data Definition Language) | CREATE, ALTER, DROP, TRUNCATE | Structure/objects (tables) |
| **DML** (Data Manipulation Language) | SELECT, INSERT, UPDATE, DELETE | Data inside tables |

## CREATE TABLE

```sql
CREATE TABLE COUNTRY (
    ID    INT NOT NULL,
    CCODE CHAR(2),
    Name  VARCHAR(60),
    PRIMARY KEY (ID)
);
```

- Primary key columns must be `NOT NULL` — the DB won't allow NULL primary keys.
- If the table already exists, `CREATE` fails → it's common to `DROP TABLE IF EXISTS` first in dev/test scripts.

## ALTER, TRUNCATE, DROP — MySQL vs DB2 syntax

| Operation | MySQL | DB2 |
|---|---|---|
| Add column | `ALTER TABLE t ADD [COLUMN] col datatype;` | same |
| Modify column type | `ALTER TABLE t MODIFY col new_type;` | `ALTER TABLE t ALTER COLUMN col SET DATA TYPE new_type;` |
| Rename column | `ALTER TABLE t CHANGE COLUMN old new datatype;` | `ALTER TABLE t RENAME COLUMN old TO new;` |
| Drop column | `ALTER TABLE t DROP COLUMN col;` | same |
| Empty all rows (keep table) | `TRUNCATE TABLE t;` | `TRUNCATE TABLE t IMMEDIATE;` |
| Delete table + data | `DROP TABLE t;` | same |

Examples:

```sql
ALTER TABLE author ADD telephone_number BIGINT;   -- new column, filled with NULLs
ALTER TABLE author MODIFY telephone_number CHAR(20);  -- numeric → CHAR to allow +, -, ()
TRUNCATE TABLE author;   -- deletes rows, NOT the table
DROP TABLE author;       -- deletes table AND its data
```

> [!tip] TRUNCATE vs DELETE vs DROP
> - `DELETE FROM t;` → removes rows (can use WHERE, logged, can be rolled back)
> - `TRUNCATE TABLE t;` → removes **all** rows fast, keeps the table structure
> - `DROP TABLE t;` → removes the table entirely, structure and all

## Relational model constraints

| Constraint | Guarantees | Enforced by |
|---|---|---|
| **Entity integrity** | Every row uniquely identifiable; no NULL/duplicate primary keys | `PRIMARY KEY` |
| **Referential integrity** | Foreign keys always point to a valid primary key in the parent table; no orphaned rows | `FOREIGN KEY ... REFERENCES` |
| **Domain integrity** | Column values are valid in type, format, range, and nullability | Data types, `CHECK`, `NOT NULL` |

```sql
CREATE TABLE BookShop_AuthorDetails (
    AUTHOR_ID   INT PRIMARY KEY,
    AUTHOR_NAME VARCHAR(100)
);

CREATE TABLE BookShop (
    BOOK_ID        INT PRIMARY KEY,                    -- entity integrity
    TITLE          VARCHAR(100) NOT NULL,              -- domain (nullability)
    PRICE          DECIMAL(5,2) CHECK (PRICE >= 0),    -- domain (range)
    PUBLISHED_DATE DATE,
    AUTHOR_ID      INT,
    FOREIGN KEY (AUTHOR_ID)                            -- referential integrity
        REFERENCES BookShop_AuthorDetails(AUTHOR_ID)
);
```

Inserting a book with an `AUTHOR_ID` that doesn't exist in the author table **fails** — that's referential integrity doing its job.

## SQL scripts

A `.sql` script = a sequence of SQL commands run in order (each terminated with `;`). Uses: create/drop tables, seed data, bulk updates/deletes, and creating **views**, **stored procedures**, and **triggers**. Typical pattern:

```sql
DROP TABLE IF EXISTS PATIENTS;
CREATE TABLE PATIENTS (
    PATIENT_ID CHAR(9)     NOT NULL,
    FIRST_NAME VARCHAR(15) NOT NULL,
    LAST_NAME  VARCHAR(15) NOT NULL,
    BIRTH_DATE DATE,
    DEPT_ID    CHAR(9)     NOT NULL,
    PRIMARY KEY (PATIENT_ID)
);
-- ...more DROP/CREATE pairs, executed sequentially
```

A primary key can also be **composite** (multiple columns), e.g. `PRIMARY KEY (LOCATION_ID, DEPT_ID)`.

## Quiz takeaways (Relational DB & Tables)

- Primary key → **uniquely identifies each row**; prevents duplicates; basis for relationships.
- Attributes of an entity become **columns**; instances become rows (tuples).
- `CREATE TABLE` is **DDL**; DDL = CREATE, ALTER, DROP (+ TRUNCATE).
- Remove table + data → `DROP`. Remove data only → `TRUNCATE`.
- Change column type (MySQL): `ALTER TABLE author MODIFY phone VARCHAR(20);`
- Add a 7-char column (MySQL): `ALTER TABLE Employees ADD ID CHAR(7);`
- The five basic SQL commands: **CREATE, SELECT, INSERT, UPDATE, DELETE**.
- Relational model is the most used because it allows **data independence**.

# Module 3 — Intermediate SQL

## Refining results: LIKE, BETWEEN, IN, ORDER BY, GROUP BY, HAVING

| Clause | Purpose | Example |
|---|---|---|
| LIKE | Pattern match with wildcards `%` (any chars) and `_` (one char) | `SELECT f_name, l_name FROM employees WHERE address LIKE '%Elgin,IL%';` |
| BETWEEN | Inclusive range (numbers, text, dates) | `SELECT * FROM employees WHERE salary BETWEEN 40000 AND 80000;` |
| IN | Match any value in a list | `SELECT * FROM Author WHERE Country IN ('Australia', 'Canada', 'India');` |
| ORDER BY | Sort ascending (default) or `DESC`; multiple columns sort in listed order | `SELECT f_name, l_name, dep_id FROM employees ORDER BY dep_id DESC, l_name;` |
| GROUP BY | Collapse identical values into groups (used with aggregates) | `SELECT dep_id, COUNT(*) FROM employees GROUP BY dep_id;` |
| HAVING | Filter **groups** after GROUP BY (WHERE filters rows *before* grouping) | `SELECT dep_id, COUNT(*) AS num, AVG(salary) AS avg_sal FROM employees GROUP BY dep_id HAVING COUNT(*) < 4 ORDER BY avg_sal;` |

> [!tip] WHERE vs HAVING
> `WHERE` filters **rows before** grouping and can't use aggregates. `HAVING` filters **groups after** aggregation — that's why "countries with more than 5 customers" needs `HAVING COUNT(CustomerID) > 5`.

Range can be written two equivalent ways:
```sql
WHERE Price BETWEEN 10 AND 25;
WHERE Price >= 10 AND Price <= 25;
```

## Built-in functions

Running functions **inside the database** (instead of pulling raw data into Python first) reduces data transferred, network bandwidth, and processing time.

### Aggregates

| Function | Returns | Example |
|---|---|---|
| COUNT() | Number of matching rows | `SELECT COUNT(dep_id) FROM employees;` |
| SUM() | Total of a numeric column | `SELECT SUM(salary) FROM employees;` |
| AVG() | Average of a numeric column | `SELECT AVG(salary) FROM employees;` |
| MIN() | Smallest value | `SELECT MIN(salary) FROM employees;` |
| MAX() | Largest value | `SELECT MAX(salary) FROM employees;` |

Alias the result with `AS`: `SELECT SUM(Cost) AS Total_Cost FROM PetRescue;`

### Scalar & string functions

| Function | Purpose | Example |
|---|---|---|
| ROUND() | Round to n decimal places | `SELECT ROUND(salary) FROM employees;` |
| LENGTH() | String length in bytes | `SELECT LENGTH(f_name) FROM employees;` |
| UCASE() / LCASE() | Upper / lower case | `SELECT DISTINCT UCASE(f_name) FROM employees;` |

### Date/time functions (MySQL)

| Function | Purpose | Example |
|---|---|---|
| DAY(), MONTH(), YEAR(), DAYOFWEEK() | Extract date parts | `SELECT DAYOFWEEK(RescueDate) FROM PetRescue WHERE Animal = 'Dog';` |
| CURRENT_DATE | Today's date | `SELECT CURRENT_DATE;` |
| DATEDIFF(d1, d2) | Days between two dates | `SELECT DATEDIFF(CURRENT_DATE, DOB) FROM Employees;` |
| FROM_DAYS(n) | Convert day count → YYYY-MM-DD | `SELECT FROM_DAYS(DATEDIFF(CURRENT_DATE, date_col)) FROM t;` |
| DATE_ADD(d, INTERVAL n unit) | Date n units later | `SELECT NAME, DATE_ADD(DOM, INTERVAL 1 YEAR) AS DOE FROM MEDS;` |
| DATE_SUB(d, INTERVAL n unit) | Date n units earlier | `SELECT DATE_SUB(date, INTERVAL 3 DAY);` |

## Sub-queries

A query nested inside another query — needed because aggregates can't go directly in WHERE (`WHERE Salary < AVG(Salary)` is **invalid**).

```sql
-- 1. Sub-query in WHERE (scalar comparison)
SELECT emp_id, f_name, l_name, salary
FROM employees
WHERE salary < (SELECT AVG(salary) FROM employees);

-- 2. Derived table / table expression (sub-query in FROM)
SELECT * FROM (SELECT emp_id, f_name, l_name, dep_id FROM employees) AS emp4all;

-- 3. Sub-query with IN
SELECT * FROM employees WHERE job_id IN (SELECT job_ident FROM jobs);

-- 4. Column expression (sub-query in SELECT)
SELECT emp_id, salary, (SELECT AVG(salary) FROM employees) AS avg_salary FROM employees;
```

## Working with multiple tables

Three ways: **sub-queries**, **implicit joins**, and **JOIN operators**.

```sql
-- Implicit inner join (join condition in WHERE)
SELECT * FROM employees, jobs WHERE employees.job_id = jobs.job_ident;

-- With table aliases
SELECT E.f_name, J.job_title
FROM employees E, jobs J
WHERE E.job_id = J.job_ident;

-- Implicit CROSS join (no condition → Cartesian product: rows₁ × rows₂)
SELECT * FROM employees, jobs;
```

### Explicit JOIN operators

*(Light in the course notes — added here because it's core interview material.)*

| JOIN | Returns |
|---|---|
| INNER JOIN | Only rows with matches in **both** tables |
| LEFT (OUTER) JOIN | All rows from left table + matches from right (NULL where no match) |
| RIGHT (OUTER) JOIN | All rows from right table + matches from left |
| FULL (OUTER) JOIN | All rows from both tables, matched where possible ("just select both") |
| CROSS JOIN | Cartesian product |
| SELF JOIN | A table joined to itself (via aliases), e.g. employee → manager |

```sql
SELECT E.f_name, D.dep_name
FROM employees E
INNER JOIN departments D ON E.dep_id = D.dept_id_dep;

SELECT E.f_name, D.dep_name
FROM employees E
LEFT JOIN departments D ON E.dep_id = D.dept_id_dep;  -- keeps employees with no dept
```

> [!note] MySQL has no native FULL OUTER JOIN — emulate with `LEFT JOIN ... UNION ... RIGHT JOIN`.

## Quiz takeaways (Refining Results / Functions / Sub-queries)

- Starts with J → `LIKE 'J%'` (% is the wildcard, not $, #, or *).
- Sort descending → `ORDER BY col DESC`; `ORDER BY name LIMIT 5` → top 5 alphabetically.
- HAVING restricts the result set of a GROUP BY.
- Alphabetical list → `ORDER BY Lastname;` (not SORT BY, which doesn't exist).
- Employees below average salary → sub-query: `WHERE Salary < (SELECT AVG(Salary) FROM Employees)`.
- Highest dept ID employees → `WHERE DEP_ID = (SELECT MAX(DEPT_ID_DEP) FROM DEPARTMENTS)`.
- Implicit join: `SELECT F_NAME, DEP_NAME FROM EMPLOYEES, DEPARTMENTS WHERE DEPT_ID_DEP = DEP_ID`.
- Days lived → `DATEDIFF(CURRENT_DATE, DOB)`; expiry a year out → `DATE_ADD(DOM, INTERVAL 1 YEAR) AS DOE`.
- Built-in functions **reduce the amount of data retrieved** to the client.

# Module 4 — Accessing Databases with Python

## Concepts

- **DB-API** — Python's standard API for connecting to relational databases (sqlite3, ibm_db, mysql-connector all follow it). One consistent interface regardless of the underlying database.
- Two main objects: **Connection** objects (manage the connection & transactions) and **Cursor** objects (run queries and traverse results).
- A **database cursor** is a control structure that enables traversal over the records in a database.
- Standard workflow: **connect → create cursor → execute SQL → fetch results → close connection**. Connections are NOT released automatically — always `close()` to free resources.

## Jupyter magic commands

- **Line magics** (`%`): apply to one line — `%pwd`, `%ls`, `%history`, `%reset`, `%who`, `%whos`, `%timeit`, `%matplotlib inline`, `%lsmagic`
- **Cell magics** (`%%`): apply to the whole cell — e.g. run another language, `%%timeit` a full cell
- **SQL magic**: `%sql sqlite:///EMP.db` connects the notebook's SQL extension to an SQLite database; then `%sql SELECT ...` or `%%sql` cells run queries directly.

## Cheat sheet: sqlite3

| Method | Purpose | Example |
|---|---|---|
| connect() | Open/create DB + connection | `con = sqlite3.connect("INSTRUCTOR.db")` |
| cursor() | Create a cursor | `cursor_obj = con.cursor()` |
| execute() | Run an SQL statement | `cursor_obj.execute('''INSERT INTO INSTRUCTOR VALUES (1, 'Rav', 'Ahuja', 'TORONTO', 'CA')''')` |
| fetchall() | All result rows as list of tuples | `output_all = cursor_obj.fetchall()` |
| fetchmany(n) | Next n rows | `output_many = cursor_obj.fetchmany(2)` |
| close() | Close the connection | `con.close()` |

```python
import sqlite3
con = sqlite3.connect("INSTRUCTOR.db")
cursor_obj = con.cursor()
cursor_obj.execute("SELECT * FROM INSTRUCTOR")
for row in cursor_obj.fetchall():
    print(row)
con.close()
```

## Cheat sheet: pandas ↔ SQL

| Method | Purpose | Example |
|---|---|---|
| pd.read_csv() | CSV → DataFrame | `df = pd.read_csv('https://data.cityofchicago.org/resource/jcxq-k9xf.csv')` |
| df.to_sql() | DataFrame → SQL table | `df.to_sql("chicago_socioeconomic_data", con, if_exists='replace', index=False, method="multi")` |
| pd.read_sql() / pd.read_sql_query() | SQL query → DataFrame (works across DB systems) | `df = pd.read_sql("SELECT * FROM INSTRUCTOR", conn)` |
| df.shape | (rows, columns) tuple | `df.shape` |
| df.describe() | Statistical summary of the DataFrame | `df.describe()` |

Visualization example: `seaborn.barplot(x='Test_Score', y='Frequency', data=df)` — bar plots show a numeric average per category; `swarmplot()` makes a categorical scatterplot.

## Cheat sheet: ibm_db (DB2)

| Method | Purpose | Example |
|---|---|---|
| connect() | Open a DB2 connection | `conn = ibm_db.connect('DATABASE=mydb;HOST=example.com;PORT=50000;UID=myuser;PWD=mypassword;', '', '')` |
| server_info() | DBMS name/version info | `server = ibm_db.server_info(conn)` |
| exec_immediate() | Execute SQL directly (no prepare/bind) | `stmt = ibm_db.exec_immediate(conn, "DROP TABLE INSTRUCTOR")` |
| close() | Close the connection | `ibm_db.close(conn)` |

## Quiz takeaways (Accessing DBs with Python)

- Connect Python to a database → **DB API** (not REST/Watson/Census APIs).
- Query SQLite from Python → `cursor.execute()`.
- Connections must be **closed explicitly** — not auto-released.
- Correct order: **connect → create & execute SQL statements → close connection**.
- `%sql sqlite:///EMP.db` → connect notebook SQL magic to SQLite.
- Cell magics: run other languages in a cell, time an entire cell.
- `pd.read_csv(...)` then `df.to_sql('Employees', conn)` → CSV becomes an SQL table in the DB.
- Two valid query patterns: `pd.read_sql(query, conn)` or `cursor = connection.execute(query)` + `fetchall()`.
- `df.to_sql('Sample', conn)` → **saves** DataFrame df to table 'Sample' via connection conn.
- `df.describe()` → statistical analysis of a DataFrame.

# Module 6 — Advanced SQL (Views, Stored Procedures, ACID)

*(Bonus module for data engineers — the original note had no content here, so this section is reconstructed as reference. Know these for interviews.)*

## Views

A **view** is a saved query that acts as a virtual table — it stores no data itself, just the query definition.

```sql
CREATE VIEW EMPSALARY AS
SELECT emp_id, f_name, l_name, salary
FROM employees
WHERE salary > 50000;

SELECT * FROM EMPSALARY;   -- query it like a table
DROP VIEW EMPSALARY;
```

Why views: simplify complex/repeated queries, restrict column access for security (show HR the salary view, not the SSN column), and present a stable interface even if underlying tables change.

## Stored procedures

A **stored procedure** is precompiled SQL stored in the database and executed on demand — encapsulates business logic, reduces network round-trips, can accept parameters.

```sql
DELIMITER //
CREATE PROCEDURE RETRIEVE_ALL()
BEGIN
    SELECT * FROM PETSALE;
END //
DELIMITER ;

CALL RETRIEVE_ALL();
DROP PROCEDURE RETRIEVE_ALL;
```

## Transactions & ACID

A **transaction** = one indivisible unit of work (one or more SQL statements that succeed or fail together). Classic example: transfer money = debit account A + credit account B — both or neither.

```sql
BEGIN;                       -- START TRANSACTION
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                      -- make permanent
-- or ROLLBACK;              -- undo everything since BEGIN
```

| ACID property | Meaning |
|---|---|
| **A**tomicity | All statements in the transaction succeed, or none do |
| **C**onsistency | The DB moves from one valid state to another (constraints hold) |
| **I**solation | Concurrent transactions don't see each other's partial work |
| **D**urability | Once committed, changes survive crashes/power loss |

`SAVEPOINT name;` sets a marker inside a transaction; `ROLLBACK TO name;` undoes only back to that marker.

# 🎯 JDA Interview Questions — SQL & Databases

Practice these out loud. Junior Data Analyst interviews (including GC/Ottawa screenings) lean heavily on tiers 1–2; tier 3 questions separate you from other juniors.

## Tier 1 — Fundamentals (expect these in every screen)

**1. What is a database, and why use one instead of a spreadsheet?**
An organized, electronically stored collection of data. Databases win on scale (millions of rows), data integrity (types, constraints), concurrent multi-user access, reduced redundancy (normalization), and query power (SQL + indexes). *(Use the comparison table above — it's your strongest prepared answer.)*

**2. What is SQL and what are its main statement categories?**
Structured Query Language — the standard language for relational databases. DDL (CREATE, ALTER, DROP, TRUNCATE) defines structure; DML (SELECT, INSERT, UPDATE, DELETE) reads/modifies data; plus transaction control (COMMIT, ROLLBACK, SAVEPOINT).

**3. What is a primary key? A foreign key?**
Primary key: uniquely identifies each row — must be unique and NOT NULL (entity integrity). Foreign key: a column referencing another table's primary key, keeping relationships valid and preventing orphaned rows (referential integrity).

**4. Difference between DELETE, TRUNCATE, and DROP?**
DELETE removes rows (supports WHERE, can be rolled back); TRUNCATE removes all rows fast but keeps the table; DROP removes the table itself, structure and data.

**5. Difference between WHERE and HAVING?**
WHERE filters rows *before* grouping and can't use aggregates; HAVING filters groups *after* GROUP BY and can (e.g., `HAVING COUNT(*) > 5`).

**6. What does DISTINCT do? What does `COUNT(DISTINCT col)` return?**
DISTINCT removes duplicate values from the result. `COUNT(DISTINCT col)` returns the number of unique non-NULL values.

**7. What happens if you run UPDATE or DELETE without a WHERE clause?**
It affects every row in the table — a classic production horror story. Habit: write the SELECT with the same WHERE first to preview affected rows.

**8. What are the `%` and `_` wildcards?**
Used with LIKE: `%` matches any sequence of characters, `_` matches exactly one. `LIKE 'J%'` → starts with J.

## Tier 2 — Core analyst skills (be ready to write these on a whiteboard/screen)

**9. Explain the types of JOINs.**
INNER (matches in both), LEFT (all left rows + matches), RIGHT (mirror), FULL OUTER (all rows both sides), CROSS (Cartesian product), SELF (table joined to itself for hierarchies like employee→manager). Interview tip: draw the two-circle Venn as you talk.

**10. Write a query: department name for each employee.**
```sql
SELECT E.f_name, D.dep_name
FROM employees E
INNER JOIN departments D ON E.dep_id = D.dept_id_dep;
```
Follow-up they love: "Include employees with no department" → switch to LEFT JOIN.

**11. Write a query: employees earning less than the average salary.**
```sql
SELECT * FROM employees
WHERE salary < (SELECT AVG(salary) FROM employees);
```
Key point: aggregates can't sit directly in WHERE — you need the sub-query.

**12. Write a query: number of customers per country, only countries with more than 5.**
```sql
SELECT country, COUNT(customer_id) AS num_customers
FROM customers
GROUP BY country
HAVING COUNT(customer_id) > 5
ORDER BY num_customers DESC;
```

**13. Write a query: top 5 areas by poverty rate.**
```sql
SELECT community_area_name
FROM census_data
ORDER BY percent_households_below_poverty DESC
LIMIT 5;
```

**14. What's a sub-query, and where can it appear?**
A query nested in another: in WHERE (scalar or IN comparisons), in FROM (derived table — must be aliased), or in SELECT (column expression).

**15. Second-highest salary? (classic)**
```sql
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
-- or: SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;
```

**16. Find duplicate emails in a table.**
```sql
SELECT email, COUNT(*) FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```

**17. How do NULLs behave?**
NULL = unknown, not zero or empty string. Test with `IS NULL / IS NOT NULL` (never `= NULL`). Aggregates like COUNT(col) and AVG skip NULLs; `COUNT(*)` counts all rows. NULLs fail JOIN equality conditions.

**18. Execution order of a SQL query?**
FROM → (JOIN) → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Explains why you can't use a SELECT alias inside WHERE (but usually can in ORDER BY).

## Tier 3 — Differentiators (advanced + Python integration)

**19. What is a view and why use one?**
A saved query acting as a virtual table (stores no data). Simplifies repeated logic, restricts sensitive columns for security, gives a stable interface over changing tables.

**20. What is a stored procedure? A trigger?**
Stored procedure: precompiled SQL saved in the DB, executed on demand (CALL), reducing round-trips and centralizing logic. Trigger: a stored procedure that fires automatically on an event (INSERT/UPDATE/DELETE), often for auditing or enforcing rules.

**21. Explain ACID with a real example.**
Atomicity, Consistency, Isolation, Durability — the guarantees of a transaction. Example: a money transfer debits one account and credits another; ACID ensures both happen or neither, concurrent transfers don't interfere, and a committed transfer survives a crash.

**22. What is normalization? When might you denormalize?**
Organizing data into related tables to remove redundancy and update anomalies (store the address once). Denormalize for read-heavy analytics/reporting, where joins are expensive and some duplication speeds queries — the typical data-warehouse trade-off.

**23. What is an index and its trade-off?**
A structure (like a book index) that lets the DB find rows without a full table scan — massive read speedup on filtered/joined columns. Trade-off: extra storage and slower writes (index must update on every INSERT/UPDATE/DELETE).

**24. How do you connect Python to a database? Walk through the workflow.**
Via a DB-API library (sqlite3, ibm_db, mysql-connector): connect → cursor → execute → fetchall/fetchmany → close. Or skip the cursor for analysis: `pd.read_sql(query, conn)` straight into a DataFrame, and `df.to_sql()` to write back.

**25. When would you do work in SQL vs pandas?**
Push filtering, joining, and aggregation into SQL — the DB is optimized for it and it minimizes data transferred. Use pandas for what SQL is weak at: complex reshaping, statistical analysis, visualization prep. Rule of thumb: reduce the data in SQL, refine it in pandas.

**26. What is SQL injection and how do you prevent it in Python?**
Malicious input concatenated into a query string ("Robert'); DROP TABLE students;--"). Prevent with parameterized queries: `cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))` — never f-strings/concatenation with user input.

**27. SQL magic in Jupyter — what's the difference between `%sql` and `%%sql`?**
`%sql` is a line magic (one statement on one line); `%%sql` is a cell magic (whole cell is SQL). Connect first with `%sql sqlite:///EMP.db`.

**28. A query is slow. What do you check?**
(1) SELECT only needed columns, not `*`; (2) filter early with WHERE; (3) check indexes on filter/join columns; (4) inspect the plan with EXPLAIN; (5) avoid functions on indexed columns in WHERE; (6) consider LIMIT for exploration.
